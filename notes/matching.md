# Matching setup

How the decompiled C is built and compared with the originals, and what to know before changing it. Toolchain choices: `notes/toolchain-vc6.md` (VC 6.0 without SP, `cl /O2`). Final scores: §5.

## 1. Layout of `src/`

| Path | Contents |
|---|---|
| `src/common/` | Code linked into happy **and** maped. `block_09.c` = happy block_09 = maped block_01 (map module); `block_01.c` = happy block_01 = maped block_03 (shared utilities). Named after happy's block. Each function carries one `// FUNCTION:` line per exe. The other look-alike functions (initialisation, shutdown, map loading, palette) differ in their code and are written once per exe (`notes/layout-maped.md` §6). |
| `src/happy/`, `src/maped/`, `src/loader/` | One `block_NN.c` per block of `notes/layout-<exe>.md` §5, functions in address order; `data.c` (globals); `<exe>.h` (declarations shared between the files of the exe). |
| `src/include/` | Headers shared between exes (`map.h`, `block_01.h`). |
| `src/crt/<exe>.h` | `// LIBRARY:` annotations of the CRT (§4). Inside `#if 0`: read by reccmp, never compiled. |

Naming (decided on 2026-10-27): files have neutral names after the blocks, with the theme in a header comment; functions and globals get a descriptive name when the code justifies it, tagged `[hypothesis]` with its evidence in a comment, otherwise `FUN_<address>` / `DAT_<address>`.

Globals are all defined in `<exe>/data.c`, in address order: the .obj that owns each one is unknown (`notes/layout-happy.md` §7). This only decides where the recompiled exe places them; it does not change the code that uses them. `reccmp-datacmp` checks their types and initial values.

## 2. Build: `scripts/build.py`

- `cl /nologo /O2 /Zi /W3 /c`, with `/I src/include /I src/<exe> /I 3rdparty/allegro-4.0.3/include`. `/W3` has no effect on the code.
- `link /SUBSYSTEM:WINDOWS /DEBUG /INCREMENTAL:NO /MAP` (`build/<exe>/<exe>.map`: placement of the globals), then `alleg40.lib` (generated by `LIB /DEF` if missing) and `kernel32.lib`; LIBC is the default library. The .obj files follow the order of `SOURCES`, i.e. the order of the blocks in the original.
- `/OPT:NOREF` by default (a function referenced only by stubs would otherwise be dropped); `--final` links with `/OPT:REF`, as the original was [hypothesis: each exe keeps only a subset of the shared files' functions, `notes/layout-maped.md` §6]. The linker option changes neither the code nor its bytes.
- **Stubs**: symbols reported unresolved by a first link get an empty definition in `build/<exe>/stubs.c`, then the link is redone. None is needed since 2026-10-27; the mechanism stays for experiments.
- **One macro per exe** (decided with the user on 2026-10-27): every source is compiled with `/DHAPPY`, `/DMAPED` or `/DLOADER`. `common/block_01.c` puts its happy-only functions (`FUN_00401000`, `read_joystick`, `read_keyboard`, `blit_to_screen`, `message_box`) and their globals' declarations (`block_01.h`) inside `#ifdef HAPPY`. Evidence [verified]: the VC6 linker reports the unresolved globals of these functions even with `/OPT:REF`, and maped has room for none of them (no `screen_mode` = 32 in its `.data`, no 512-byte gap for `keys[128]` in its `.bss`); two separate files could not reproduce happy's order, where the shared functions are interleaved with the others. [hypothesis] The original used conditional compilation or a reduced copy of the file; the macro name is ours. It changes no code.
- Finally, `reccmp-project detect --what recompiled` writes `reccmp-build.yml`. **Build happy and maped together** (`build.py happy maped`, or no argument): `detect` rewrites the file with the targets of the current build only.
- After editing a source, rebuild before running reccmp: annotations are matched through the line numbers of the PDB.

## 3. reccmp

- `reccmp-project.yml` (versioned): targets `HAPPY`, `MAPED`, `LOADER` with the SHA-256 of the originals, `source_root: src` (so that `3rdparty/` is not scanned), and the CSV data sources of §3 below.
- `reccmp-user.yml` (paths of the originals) and `reccmp-build.yml` are per machine and ignored by git. On a new machine: `reccmp-project create --originals game/happy.exe game/maped.exe game/loader.exe` in a scratch folder and copy its `reccmp-user.yml`, or write it by hand (3 lines per target).
- One function: `python scripts/reccmp_run.py --target HAPPY --verbose 0x00406c80` (same arguments as `reccmp-reccmp`, run with the Python where reccmp is installed). All functions: `scripts/progress.py`, which writes `notes/data/progress-<exe>.csv`. Data: `reccmp-datacmp --target HAPPY`.
- On Windows, a 100% match prints an emoji that the cp1252 console cannot encode: set `PYTHONIOENCODING=utf-8`.

**End-of-array operands** (decided with the user on 2026-10-27). A loop over a whole global array compiles to `cmp reg, &array[N].field`, an address past the array (or just before it: `enter_hiscore`, `hiscores[0].name - 1`). reccmp names it after whatever variable follows: an unannotated address in the original (`0x414134`), another annotated variable in the rebuilt exe, and counts a difference on identical code (14 functions of happy, 5 of maped). The layout of the globals cannot be reproduced [verified, test programs]: uninitialised globals are COMMON, placed by the linker in an order that depends on their (unknown) original names. So `scripts/reccmp_run.py` wraps reccmp-reccmp 0.1.7 (patched at run time, package unchanged): two operands of lines aligned one to one are equal when their addresses are at the same offset of one matched variable, at most 64 bytes outside it. `--audit` lists every line treated that way: in the game code, only end-of-array `cmp` operands and `hiscores - 1`; in the CRT, unannotated CRT variables next to `errno` / `wind`. Residual risk: a wrong global at the same distance from the same variable would pass (covered by `reccmp-datacmp` and the other uses of the variable). Plain `reccmp-reccmp` shows these functions below 100%.

Annotation pitfalls [verified]:
- An annotation followed by a macro call that ends in `);` (`END_OF_MAIN();`) is taken for a declaration and silently dropped. Use a lookup by name: a comment line with the undecorated symbol name right after the annotation (`// WinMain`; `// _WinMain@16` is not found).
- `allegro.h` defines `main` as `_mangled_main`: reccmp and `progress.py` show `main` under that name.
- A call to an unannotated function counts as a difference (`<OFFSETn>` against `FUN_...`): annotate the callee.
- **String literals need a `// STRING:` annotation**, one line per exe, right before the line that holds the literal (inside a function body is fine), including an inline `strcpy` of a literal. Without it the literal is named on the rebuilt side only. A marker before a call whose literal is on the next line makes reccmp drop the whole function ("Failed to find a match at address"; `reccmp-decomplint <file>` reports `no_suitable_name`). reccmp takes the first literal of the line: split calls and initialisers so that each line holds one literal (`save_settings`, `set_controls`). Pooled strings (`/Gf`) are annotated once.
- **Floating-point constants** of `.rdata` (`fmul qword ptr [0x4111e0]`) are named by value on the rebuilt side only: their original address is declared in a CSV data source (`reccmp/happy.csv`: `0x004111e0,float,8`; `reccmp/maped.csv`: `0x0040d1c8`), listed under `data_sources` in `reccmp-project.yml`.
- **CRT variables** and Allegro inline code emitted out of line are annotated by the undecorated name of the rebuilt PDB: `// GLOBAL: HAPPY 0x00413b3c` then `// errno`; `// LIBRARY: HAPPY 0x00402110` then `// _set_errno_erange`.
- **Pointers to import thunks in initialised data** (maped's `DIALOG` arrays point at the `jmp [IAT]` thunks `0x00405CA0`-`0x00405CC4`): `reccmp-datacmp` names them only if annotated, `// LIBRARY: MAPED 0x00405cb2` then `// _d_text_proc`, in an `#if 0` block of `src/maped/data.c`.
- `DATAFILE` entries are 16 bytes (`dat`, `type`, `size`, `prop`): `[misc_datafile + 0x40]` is `misc_datafile[4].dat`.

**OLDNAMES aliases** [verified]. `chdir` and `_chdir` give the same code but not the same CRT layout: the linker resolves the OLDNAMES alias in a later pass, so `chdir` puts `__chdir` and what it pulls in (`__dosmaperr`, `__mbctoupper`) at the end of the CRT, as in the originals (loader `0x00404226`); with `_chdir` the whole CRT shifted (loader 0/68 CRT functions at their address, 68/68 with `chdir`). The sources therefore call `chdir`, and `itoa` in happy (`draw_level`); reccmp names the targets `_chdir` and `_itoa`, the names used in `src/crt/`. Open: happy's Rich header counts two `AliasObj60` where the sources use three aliases (`itoa`, `stricmp`, `strcmpi`); which spelling is wrong is not observable, and the tail of happy's CRT is in another order than the original for every combination tried [hypothesis: the original objects referenced more CRT symbols than the functions kept by `/OPT:REF`]. Scores do not depend on it: CRT calls are compared by name.

**Whole-exe check (loader)** [verified 2026-10-27]: the objects of `build.py --final loader`, linked again without `/DEBUG` (`link /SUBSYSTEM:WINDOWS /INCREMENTAL:NO /OPT:REF`, same libraries), give `.text`, `.rdata` and `.data` byte-identical to the original loader.exe; only `.rsrc` (the icon) is missing. With `/DEBUG`, `.rdata` holds the debug directory and grows by `0x28`.

## 3a. VC6 code-generation shapes [verified]

Why some of the C looks the way it does. Each of these changed the generated code, so editing a function back into a "cleaner" form will usually break its match. The function named is the one where the shape was found.

Statement order and variables:
- VC6 keeps the source order of independent stores (constants in registers come first) (`FUN_00401000`, `FUN_004019C0`).
- Which local gets a parameter's stack slot depends on the order of the first assignments, not of the declarations (`take_item`). Initialisers (`int done = 0;`) and assignments order the first loads differently (`play_level`).
- A local initialised just before its loop can live in a register; initialised at the top, it goes to the stack (`bonus_room`). A variable zeroed at the top of the function can move an `xor` before an `imul` (`auto_mask`).
- The position of a copy relative to a neighbouring load can change the registers of a whole branch (`auto_mask`: `n = tiles[i].t1 - 1; old = m;`); `old = sel` before or after a call decides stack or register (`main_menu`).
- Reusing one variable for unrelated values can be what the original did: `play_game` (call result into the loop counter `i`), `bonus_room` (one variable for two loops), `resize_map` (the parameters reused as temporaries).
- A separate local for a derived value rather than updating in place (`editor_loop`: `x = DAT_0042a420 * 16 + mx`); a file offset computed into a local before `fopen` (`load_objects`); `x + y` versus `y + x` decides which global is loaded first (`editor_loop`).
- A coordinate derived from a loop index is written in the expression (`i * 16 - sx`, `MIN(i + dx, w - 1)`, `row * 18`) rather than kept in a variable: VC6 creates its own induction variable with the original slots, tests and preheader (`draw_level`, `shift_map`, `pick_tile`). Conversely, separate induction variables in the `for` header where the original has them (`blit_to_screen`).
- A value used in two calls is written as the same expression twice rather than through a local (`draw_slot_panel`); a local for a nested call's result lets VC6 group the stack cleanups (`draw_level`, `len = text_length(...)`).
- `num_bonus = num_normal = 0;` rather than two assignments (loader `main`).
- `volatile` on the globals written by timer callbacks (`timer_ticks`, `time_left`, `fps`, `frame_count`).

Types:
- A value kept in `eax` up to the `ret` means the function returns it, even if callers ignore it (`FUN_004019C0`, `bonus_room` returns its last call's value).
- A local that saves a byte field is an `int` (`load_level`); an `unsigned int` field keeps `10000 - i * 1500` from being reduced (`init_hiscores`).
- A byte global loaded as `mov ecx, dword ptr [g]` / `and ecx, 0xff` (rather than `xor ecx, ecx` / `mov cl, [g]`) is a member at an aligned offset of a structure or array: this is how `PLAYER player` (`0x0042F500`-`0x0042F567`, `happy.h`) was found (decided with the user on 2026-10-27).

Control flow:
- `strcpy` in both branches rather than a pointer chosen by an `if` (`message_box`); `do`/`while` when there is no test before the first iteration (`message_box`).
- An `if`/`else` whose branches call the same function with one different argument is merged into one call; a `?:` in the argument is not (`bonus_room`). Two `?:` on the same condition compile like an `if`/`else` but with other registers (`custom_game`). A `?:` between constants that differ by one and the `if`/`else` give the same instructions, but only the `if`/`else` gave the original registers (`FUN_004019b0`).
- `while (!done)` versus `do`/`while` when `done` is known on a path (`custom_game`). A loop whose first block is a conditional exit is rotated by `/O2` whatever the C shape, except a `while (!done)` on a flag set in the body: the original `main` and `custom_game`.
- Nested `if`s versus an `else if` chain: the block order follows the nesting (`custom_game`). Separate `if`s rather than `else if` when each branch ends the function (`draw_tile_mask`, `draw_tile_type`).
- VC6 merges identical sequences at the start and end of two branches after register allocation, so branches that get the same registers share code (`auto_mask`).
- Two identical calls written as separate branches give VC6 one more path when choosing what to keep in a register, and are merged afterwards (`set_screen_mode`: `if (mode) f(320); else if (SCREEN_W == 320) {...} else f(320);`).
- Comparisons: `i <= 15` gives `jle`, `i < 16` gives `jl` (`select_help_text`, `pick_tile`); `x <= -1` gives `cmp eax, -1` / `jg` where `x < 0` gives `test` / `jge`.

Macros and library code:
- `MIN(a + 1, 3)` assigned to a global (compute, store, compare, store the constant) differs from `if (++g >= 3) g = 3` (`take_item`, `kill_player`); `MID(0, 18, i)` gives `jg`, `MID(0, i, 18)` `jge` (`enter_hiscore`, `enter_password`); the arguments of `MIN`/`MAX` in the original order (`play_level`); `m = MAX(m, old); t->t2 = m;` rather than `t->t2 = MAX(m, old);` (`auto_mask`).
- `!x & 1` on a byte (`take_item`); `abs()` is inlined as `cdq` / `xor` / `sub`, Allegro's `ABS` as compare and `neg`; Allegro's `TRUE` is -1 (`play_level`).
- `fmul` (the Allegro 3.x alias kept by `alcompat.h`) rather than `fixmul` in `play_level`: same code per product, but VC6 adds into the product's register (`0x004050DA`); the other functions keep the 4.0 names. A function that calls `fixtoi` has an `ebp` frame (`fixfloor` is inline asm, `draw_level`).
- Allegro inline functions recognised by their vtable offset (`GFX_VTABLE`, `allegro/gfx.h`): `+0x40`/`+0x44` with `cmp [vtable], 8` = `draw_sprite`, `+0x48` = `draw_sprite_v_flip`, `+0x4c` = `draw_sprite_h_flip`, `+0x38` = `rectfill`. `object_message` is inline (`allegro/inline/gui.inl`): `acquire_screen` / `proc(MSG_DRAW)` / `release_screen` (`FUN_004015d0`).
- `FUN_00403e00` matches only when written like `check_pp_collision` of Ivan Baldo's PPCol library (bounding-box test with early return, shifts, `maxw`/`maxh` decremented, nested loops from the end).
- `""` is a 1-byte COMDAT in `.bss` for cl 12, placed at the start of `.bss` (loader `0x00406708`).

When a function is close but not at 100%: compile its file with the project flags and `/FAs`, compare the listing with the original, and try the orders or forms above. Often several orders give the same code: the source order is then not observable, and the comment in `src/` says so.

## 3b. Ghidra

`scripts/ghidra_sync.py` carries `src/` into Ghidra (dry run by default; `--apply` writes, `--save` writes then saves). It reads the `FUNCTION`, `LIBRARY` and `GLOBAL` annotations (not `src/crt/`) and only calls `import_data_types`, `create_function`, `rename_function`, `rename_symbol`, `set_function_prototype` and `apply_data_type`, with `strict_mode=off` (the server's naming gate wants PascalCase and a `g_` prefix, which `src/` does not use). From a fresh import of the three exes, `--save happy maped loader` rebuilds the reference project (decided with the user on 2026-10-28: no `.gar` to carry between machines; the project holds the game binaries, which are never published):
1. structures of `src/include`, `src/common` and `src/<exe>` used by the annotations are compared field by field (the script computes the MSVC layout) and imported when missing or different; importing an existing name replaces the type in place. `fixed` becomes `int`, Allegro's types (`BITMAP`, `DATAFILE`…) `void *`; `char x[N][NAME_SIZE]` gets a typedef `NAME`;
2. functions the analysis missed are created (happy `timer_1s`, `timer_15ms`, `main`; maped `slider_changed`, `main`, the 7 `d_*_proc` thunks; loader `main`), then the script waits for the auto-analysis;
3. names and prototypes; 4. global names and types. When a type would clear data items that start inside it, items with generated names are reset to `undefined` first; an item named in `src/` stops it.

A `DAT_<address>` name of `src/` keeps Ghidra's default name. Import thunks keep Ghidra's import name (`d_check_proc` for `_d_check_proc`). Not tested end to end on a fresh import (only on the synced project, and each step in dry run).

Pitfalls [verified 2026-10-27]:
- **Auto-analysis queue**: every write queues analysis tasks; a `save_program` sent while they run waits behind them and blocks the whole HTTP server. `--save` waits for `analysis_status` to report `analyzing: false`. A write can also fail during the analysis ("Invalid signature") and succeed afterwards.
- **Do not use `modify_struct_field` / `add_struct_field`**: retyping a field shrank `OBJ` from 28 to 16 bytes. Repair by re-importing the structure.
- `rename_symbol` on an address without defined data creates a label.

## 4. CRT names

The local `LIBC.LIB` is the game's (`notes/toolchain-vc6.md`). The `LIBRARY` annotations of `src/crt/<exe>.h` were generated (by `scripts/crt_names.py`, removed once done, see git history) by matching each CRT function of the originals with a symbol of a code section of `LIBC.LIB` whose bytes are identical, relocations and trailing padding ignored. Ambiguities were resolved through the relocations; asm bodies with internal labels (`_memcpy`, `_memmove`, `__global_unwind2`, `__local_unwind2`) are compared up to the end of the section; aliases at the same offset keep Ghidra's name (`__strcmpi` = `__stricmp`). Names are those the rebuilt game code calls, since reccmp names a call target after the rebuilt PDB: `__alloca_probe` -> `__chkstk` (cl calls the second for a frame over 4 KB, loader `main` `0x00401005`), `__chdir` -> `_chdir` and `__itoa` -> `_itoa` (OLDNAMES, §3). Per-function results, with the `.obj` member: `notes/data/crt-<exe>.csv`.

| exe | CRT functions | named | import thunks (not annotated) | ambiguous | not found |
|---|---:|---:|---:|---:|---:|
| happy | 155 | 152 | 1 | 1 (`0x0040B376`, `ret`: `__fpclear` or `__rttosnpop`) | 1 (`0x0040DF22`, 34 B, after `__local_unwind2`) |
| maped | 173 | 163 | 8 | 1 (`0x00405FFF`, same `ret`) | 1 (`0x00409652`) |
| loader | 68 | 66 | 1 | 0 | 1 (`0x0040237E`) |

Named: 152 + 163 + 66 = 381 annotations.
