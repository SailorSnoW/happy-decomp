# Matching setup

How the decompiled C is built and compared with the originals. Started on 2026-10-27, branch `decomp/happy`. Toolchain choices: `notes/toolchain-vc6.md` §6 and `notes/decompme-candidates.md` §11 (VC 6.0 without SP, `cl /O2`).

## 1. Layout of `src/`

| Path | Contents |
|---|---|
| `src/common/` | Code linked into happy **and** maped. `block_09.c` = happy block_09 = maped block_01 (map module); `block_01.c` = happy block_01 = maped block_03 (shared utilities). Named after happy's block. Each function carries one `// FUNCTION:` line per exe. |
| `src/happy/`, `src/maped/`, `src/loader/` | One `block_NN.c` per block of `notes/layout-<exe>.md` §8, functions in address order; `data.c` (globals); `<exe>.h` (declarations shared between the files of the exe). |
| `src/include/` | Headers shared between exes (`map.h`, `block_01.h`). |
| `src/crt/<exe>.h` | `// LIBRARY:` annotations of the CRT, generated by `scripts/crt_names.py`. Inside `#if 0`: read by reccmp, never compiled. |

Naming (decided on 2026-10-27):
- files: neutral names after the blocks, theme in a header comment;
- functions and globals: a descriptive name when the code justifies it, tagged `[hypothesis]` with its evidence in a comment; otherwise `FUN_<address>` / `DAT_<address>`.

Globals are all defined in `<exe>/data.c`, in address order, until the .obj that owns each one is known (`layout-happy.md` §9, questions 1 and 7). This only decides where the recompiled exe places them; it does not change the code that uses them. `reccmp-datacmp` checks their types and initial values.

## 2. Build: `scripts/build.py`

- `cl /nologo /O2 /Zi /W3 /c`, with `/I src/include /I src/<exe> /I 3rdparty/allegro-4.0.3/include`. `/W3` has no effect on the code.
- `link /SUBSYSTEM:WINDOWS /DEBUG /INCREMENTAL:NO /MAP` (`build/<exe>/<exe>.map`: placement of the globals), then `alleg40.lib` (generated by `LIB /DEF` if missing) and `kernel32.lib`; LIBC is the default library. The .obj files follow the order of `SOURCES`, i.e. the order of the blocks in the original. Missing files are skipped.
- **`/OPT:NOREF` during the decompilation** [verified 2026-10-27]: with `/OPT:REF`, the five decompiled functions disappeared from the exe because their callers are still stubs. reccmp then reported "Failed to find function symbol". `--final` links with `/OPT:REF`, as the original was linked [hypothesis, `notes/shared-code.md`]. The linker option changes neither the code nor its bytes (`notes/toolchain-vc6.md` §6).
- **Stubs**: the symbols the first link reports as unresolved get an empty definition in `build/<exe>/stubs.c` (`void f(void) {}`, or `__stdcall` with as many `int` as `@N` says), then the link is redone. The stubs carry no annotation, so reccmp ignores them. The exe cannot be run while stubs remain. The list of stubs is in practice the list of functions that are called but not decompiled yet.
- **One macro per exe** (decided with the user on 2026-10-27): every source is compiled with `/DHAPPY`, `/DMAPED` or `/DLOADER`. `common/block_01.c` puts its happy-only functions (`FUN_00401000`, `read_joystick`, `read_keyboard`, `blit_to_screen`, `message_box`) and their globals' declarations (`block_01.h`) inside `#ifdef HAPPY`. Evidence [verified]: the VC6 linker reports the unresolved globals of these functions even with `/OPT:REF`, which would drop them, and maped has room for none of them (no `screen_mode` = 32 in its `.data`, no 512-byte gap for `keys[128]` in its `.bss`), so the original maped was not linked with them; two separate files could not reproduce happy's order, where the shared functions are interleaved with the others. [hypothesis] The original used conditional compilation or a reduced copy of the file; the binaries cannot tell them apart, and the macro name is ours. Before this, maped needed 8 data stubs (generated as functions); now no stub is left in either exe and both final links (`--final`) succeed. The macro changes no code (same scores, `reccmp-datacmp` 0 issues).
- Finally, `reccmp-project detect --what recompiled` writes `reccmp-build.yml`.

## 3. reccmp

- `reccmp-project.yml` (versioned): targets `HAPPY`, `MAPED`, `LOADER`, `source_root: src`. It was created by `reccmp-project create --originals game/happy.exe game/maped.exe game/loader.exe`, then `source_root` was changed from `.` to `src`, so that `captures/` (the smoke test, which annotates `HAPPY` too) and `3rdparty/` are not scanned.
- `reccmp-user.yml` (paths of the originals) and `reccmp-build.yml` are per machine and ignored by git. On a new machine: `reccmp-project create` in a scratch folder and copy its `reccmp-user.yml`, or write it by hand (3 lines per target).
- Per function: `python scripts/reccmp_run.py --target HAPPY --verbose 0x00406c80` (reccmp-reccmp with the end-of-array operands compared by offset, below; same arguments; the global Python where reccmp is installed).
- Progress: `scripts/progress.py`. It keeps only the GAME functions of `notes/data/functions-<exe>.csv` and writes `notes/data/progress-<exe>.csv`.

Pitfalls [verified]:
- An annotation followed by a macro call that ends in `);` (`END_OF_MAIN();`) is taken by reccmp's parser for a declaration and silently dropped. Lookup by name instead: a comment line with the symbol name right after the annotation (`// WinMain`, undecorated; `// _WinMain@16` is not found).
- `WinMain` (`0x0040A970`) was at 91.67% while `main` was a stub: the only difference was `push main`, which pointed at an unannotated function. 100% since `main` is annotated (2026-10-27).
- `allegro.h` defines `main` as `_mangled_main`: reccmp, `progress.py` and the `/FAs` listings show `main` (`0x0040A830`) under that name (`__mangled_main` in the listing).
- Same for any call to a function that is not decompiled yet: `call <OFFSETn>` on the original side, `call FUN_...` on the recompiled side. None left on 2026-10-27 (all of happy is annotated). They disappear when the callee is annotated [verified: the six callers of `draw_level` that only differed by the call went to 100%].
- **String literals need a `// STRING:` annotation** (one line per exe, right before the line that uses the literal; inside a function body is fine). Without it, reccmp names the literal on the recompiled side (`"unnamed" (STRING)`) but not on the original side (`<OFFSET3>`), and counts a difference: `map_create` was at 96.72% with identical code. An inline `strcpy` of a literal (`mov` of dwords from the string) is concerned too. Pooled strings (`/Gf`, `layout-happy.md` §6) are annotated once.
- **End-of-array pointers** [verified 2026-10-27]: a loop over a whole global array compiles to `cmp reg, &array[N].field`, an address past the array. reccmp names it after whatever variable follows the array: in the original an unannotated address (`0x414134`), in the recompiled exe another annotated variable (`use_joystick`), so it counts a difference on identical code. `FUN_00401000` (98.18%), `FUN_00401160` (98.75% in happy, 100% in maped, where the neighbour happens to be the same), `draw_particles` (98.53%), `draw_objects` (99.16%), `load_level_objects` (98.15%), `FUN_00403130` (95.45%), `load_level` (99.28%), `reset_player` (98.39%), and in block_05 `FUN_00403f60` (99.26%), `FUN_00404110` (98.39%), `update_objects` (99.51%), `start_level` (97.56%, also a call to `0x00402620`) and `bonus_room` (one of its three differences), and in block_06 `clear_objects` (83.33%, a 19-byte function) are in that case: 14 functions on 2026-10-27. A pointer just **before** an array is the same case: `enter_hiscore` (99.55%) writes `name[i - 1]` through `hiscores[0].name - 1` (`0x413d5f`), which reccmp names on neither side, every one checked by reading its diff (the end-of-array operand is the only line). The order of the uninitialised globals (COMMON) in the recompiled exe is chosen by the linker, neither by address nor by source order (`build/happy/happy.map`), so this cannot be fixed from `data.c`. **Decided with the user on 2026-10-27**: no initialiser or other trick to force the layout of the globals. **Then decided with the user (same day)**: these operands are compared on the comparison side, by `scripts/reccmp_run.py`, a wrapper of reccmp-reccmp 0.1.7 (patched at run time, package unchanged): two operands of lines aligned one to one are equal when their addresses are at the same offset of one matched variable, at most 64 bytes outside it (`DAT_00414140+0xb0a (OFFSET)` on both sides). `progress.py` uses it; all 15 functions above (and the 5 of maped) are at 100%, the code being unchanged. `--audit` lists every line it treated as equal: in the game code, only end-of-array `cmp` operands and `hiscores - 1` [verified]; in the CRT, also unannotated CRT variables next to `errno` / `wind`, at the same offset in both exes. A wrong global that sits by chance at the same distance from the same variable would pass: the residual risk, covered by `reccmp-datacmp` and the other uses of the variable. Plain `reccmp-reccmp` still shows these functions below 100%.
- Why the layout cannot be reproduced [verified 2026-10-27, test programs]: the uninitialised globals are COMMON; the linker places them in the reverse order of the compiler's symbol table, which depends on the names (same declarations with other names give another order), and the original names are unknown. Globals initialised to 0 or `static` go to the `.bss` of their object instead (`int x = 0;` included), before the CRT's: that is where the original has `0x00413B10`-`0x00413B34`, but no array is concerned.
- **One literal per line**: reccmp takes the first string literal of the line that follows a `// STRING:` marker, so two literals on one line (`fopen("happy.sav", "wb")`) need the call split, with a marker before each line (`save_settings`). Same for an array initialiser: one element per line, each after its marker (`set_controls`, `names[5]`: 97.58% -> 100%).
- **`DATAFILE` entries are 16 bytes** (`dat`, `type`, `size`, `prop`): `[misc_datafile + 0x40]` is `misc_datafile[4].dat`, not `[8]`.
- **CRT variables** are annotated by name like the functions, with the name the recompiled PDB gives (undecorated): `// GLOBAL: HAPPY 0x00413b3c` then `// errno` (`// _errno` is not found). Same for the inline function of `al386vc.h` emitted out of line: `// LIBRARY: HAPPY 0x00402110` then `// _set_errno_erange` (100%).
- **Floating-point constants** of `.rdata` (`fmul qword ptr [0x4111e0]`): reccmp names them by value (`0.0625 (FLOAT)`) on the recompiled side only. The original address is declared in a CSV data source, `reccmp/happy.csv` (`address,type,size` / `0x004111e0,float,8`), listed under `data_sources` of the target in `reccmp-project.yml` [verified: `init_level_palette` 100%]. maped: `reccmp/maped.csv` (`0x0040d1c8`, the same 0.0625, `FUN_00401400`).
- **Build both exes together** (`build.py happy maped`): `reccmp-project detect` rewrites `reccmp-build.yml` with the targets of the current build only, and the other target then fails with "missing data: recompiled_path".
- **reccmp output on Windows**: a 100% match prints an emoji that the cp1252 console cannot encode (`UnicodeEncodeError`). Set `PYTHONIOENCODING=utf-8`.
- After editing a source, rebuild before running reccmp: annotations are matched through the source line numbers of the PDB, and a shifted line gives "Failed to find function symbol".
- **A `// STRING:` marker must precede the line that holds the literal** [verified 2026-10-27, maped `draw_editor`]: a marker before a call whose literal is on the next line makes reccmp drop the whole function silently ("Failed to find a match at address"); `reccmp-decomplint <file>` reports it as `no_suitable_name`. Run it on new files.
- **Pointers to import thunks in initialised data** [verified 2026-10-27, maped]: the `proc` fields of the `DIALOG` arrays point at the `jmp [IAT]` thunks of `alleg40.lib` (`0x00405CA0`-`0x00405CC4`, `notes/layout-maped.md` §5). `reccmp-datacmp` names them only if they are annotated: `// LIBRARY: MAPED 0x00405cb2` then `// _d_text_proc`, in an `#if 0` block of `src/maped/data.c`.
- **OLDNAMES aliases** [verified 2026-10-27, maped and loader `main`]: `chdir` is an alias of `_chdir` at the same address (`build/maped/maped.map`), and reccmp names the call target `_chdir`. Calling `chdir` or `_chdir` gives the same code, **but not the same CRT layout**: the linker resolves the OLDNAMES alias in a later pass, so `chdir` puts `__chdir` and the functions it pulls in (`__dosmaperr`, `__mbctoupper`) at the end of the CRT, as in the originals (loader `0x00404226`, after `_memset`). With `_chdir`, they came first and shifted the whole CRT: loader 0/68 CRT functions at their original address, maped 17/163; with `chdir`, loader 68/68 and maped 162/163. The sources therefore call `chdir`, and `crt_names.py` annotates `0x00404226` (loader) / `0x0040C516` (maped) under the name of the alias, `_chdir` (`COMPILER_ALIASES`, §4). Same for **`itoa`** in happy (`draw_level`): reccmp names the target `_itoa`, so `0x00410CAC` is annotated `_itoa` (it was `__itoa`, the last two differences of `draw_level`).
- **happy's OLDNAMES aliases** [verified 2026-10-27]: the original's Rich header counts `AliasObj60 ×2`, the rebuilt exe `×3`: the sources call `itoa`, `stricmp` (`enter_password`) and `strcmpi` (`main`). One of them is not the original spelling; the code is the same for all of them (`stricmp` and `strcmpi` are the same function, `0x00410C20`). The CRT layout does not tell which: with `--final`, the game code ends at `0x0040AD50` as in the original, but the CRT objects are already in another order from `fflush.obj` (pulled right after `fread.obj` in the original, after `_freebuf.obj` here), and the tail is `xtoa.obj`, `stricmp.obj`, `ulldiv.obj`, `ullrem.obj` for every combination tried (`itoa` + `stricmp`, `itoa` + `strcmpi`, all three), where the original has `stricmp.obj` then `xtoa.obj`, `ulldiv.obj` earlier. [hypothesis] The original game objects referenced more CRT symbols than the functions kept in the exe (code discarded by `/OPT:REF`, which still pulls the library members). The scores do not depend on it: CRT calls are compared by name.
- **Whole-exe check (loader)** [verified 2026-10-27]: the objects of `build.py --final loader`, linked again without `/DEBUG` (`link /SUBSYSTEM:WINDOWS /INCREMENTAL:NO /OPT:REF`, same libraries), give `.text`, `.rdata` and `.data` **byte-identical** to the original loader.exe; only `.rsrc` (the icon, cvtres) is missing. With `/DEBUG`, `.rdata` holds the debug directory and grows by `0x28`, which shifts the 20 `.rdata` addresses in `.text`.

## 3a. Shapes that matter [verified 2026-10-27]

Code-generation clues met so far, to try first when a function is close:
- order of independent stores: VC6 keeps the source order (constants in registers come first), so a different order of stores means a different order of statements (`FUN_00401000`, `FUN_004019C0`);
- `volatile` on globals written by a timer callback (`timer_ticks`, `time_left`, `fps`, `frame_count`): their loads and stores are not moved across the prologue or other stores;
- separate induction variables (two counters in the `for` header) instead of `x * 2` (`blit_to_screen`);
- `unsigned int` field: `10000 - i * 1500` is not reduced to a decreasing induction variable (`init_hiscores`);
- a value kept in `eax` up to the `ret` although the caller ignores it: the function returns it (`FUN_004019C0`);
- a local that saves a byte field is an `int` (stored as a dword): `load_level`;
- `strcpy` in both branches of an `if` rather than a pointer chosen by the `if` (`message_box`);
- no test before the first iteration: `do`/`while` (`message_box`).
- the other shapes found in block_05 (2026-10-27):
  - `MIN(a + 1, 3)` assigned to a global compiles to "compute, store, compare, conditionally store the constant" (`lea eax, [ecx+1]` / `mov [g], eax` / `jl` / `mov [g], 3`), unlike `if (++g >= 3) g = 3` (`inc`): `take_item`, `kill_player`;
  - `!x & 1` on a byte gives `xor eax, eax` / `test cl, cl` / `sete al` / `test al, 1`, which `!x` alone does not (`take_item`);
  - an `if`/`else` whose branches call the same function with one different argument is merged by VC6 into a single call after the branch (`bonus_room`, the two "Thanks for taking..." texts); a `?:` in the argument gives different code;
  - which local gets a parameter's stack slot depends on the order of the first assignments, not on the order of the declarations (`take_item`: `take = 1` before the index computation);
  - a local only initialised just before the loop that uses it can live in a register for the whole function, where an initialisation at the top sends it to the stack (`bonus_room`, `frame`);
  - `FUN_00403e00` only matched once written like `check_pp_collision` of the PPCol library (Ivan Baldo): bounding-box test with early return, shifts, `maxw`/`maxh` decremented, start/end variables, nested loops from the end; the intermediate variables decide the register allocation;
- the shapes found in block_07 (2026-10-27):
  - a clamp `MID(0, 18, i)` (Allegro's `MAX(0, MIN(18, i))`) tests `i > 18` with `jg`; `MID(0, i, 18)` gives `jge`, and two `if`s give another layout (`enter_hiscore`, `enter_password`);
  - a variable reused for an unrelated value can be what the original did: in `play_game`, the result of `0x00404C50` goes into the loop counter `i` (both in `esi`); with a separate variable, VC6 propagates the known value 1 and writes `mov ebp, 1` instead of `mov ebp, esi`;
  - the position of `old = sel` relative to a call decides whether `old` lives on the stack or in a register (`main_menu`: before the Space/Enter test, which may call `options_menu`);
  - Allegro's inline sprite functions, recognised by the vtable offset of the call: `+0x40`/`+0x44` with a `cmp [vtable], 8` = `draw_sprite`, `+0x48` = `draw_sprite_v_flip`, `+0x4c` = `draw_sprite_h_flip`, `+0x38` = `rectfill` (`GFX_VTABLE`, `allegro/gfx.h`);
  - a function whose last statement is a call and whose caller reads `eax` returns that call's value (`bonus_room` now `int`, same code);
- the shapes found in block_08 (2026-10-27):
  - a value used in two calls written as the same expression twice (`x1 + (x2 - x1) / 2`, merged by VC6) rather than assigned to a local or to the parameter: the choice decides which registers the parameters get (`draw_slot_panel`, 80.85% with `x1 +=`, 90.05% with a local, 100% with the expression);
  - two `?:` on the same condition (`x = screen_mode ? ... : ...; y = screen_mode ? ... : ...;`) are compiled as one test and one branch, like an `if`/`else`, but give the variables other registers: only the `?:` form matched (`custom_game`, found by trying the shapes in a loop);
  - `while (!done) { ... }` and `do { ... } while (!done)` differ when `done` is known to be 0 on a path: with `do`/`while`, VC6 sends that path straight to the top of the loop; with `while`, to the test (`custom_game`). The `while` form also places the code after the loop before an early `return` of the body;
  - nested `if (a) { if (b) x; else f(1); } else f(2);` versus `if (!a) ... else if (!b) ...`: the block order follows the nesting (`custom_game`, "Play!");
  - an assignment of a constant equal to a register known on that path is stored from the register (`mov [done], esi` in the `b == 1` branch of `custom_game`);
  - a loop controlled by an index whose coordinate is derived from it (`for (j = 0; j < 14; j++) { y = j * 16; ...`) is compiled with the test on the coordinate (`cmp edi, 0xe0`) and keeps the index when it is used elsewhere; written with two counters in the header and the test on the coordinate, VC6 can drop the index instead (`draw_level`, notes/block03-diffs.md; the final form has no `y` at all, see below);
  - a function that calls `fixtoi` has an `ebp` frame: `fixfloor` is inline asm in `al386vc.h` (`draw_level`);
  - in `play_level` (2026-10-27): initialisers (`int done = 0; int last = time_left;`) instead of assignments change the order of the first loads; the arguments of `MIN`/`MAX` in the original order (the limit first); `abs()` is inlined as `cdq` / `xor` / `sub`, Allegro's `ABS` as a compare and `neg`; `x <= -1` gives `cmp eax, -1` / `jg` where `x < 0` gives `test` / `jge`; Allegro's `TRUE` is -1 (`c ? FALSE : TRUE` gives `neg` / `sbb` / `neg` / `dec`);
  - a small loop whose first block is a conditional exit (`call` / `test` / `jcc`) is rotated by VC6 `/O2`: the head is copied at the bottom and the exit block placed after the loop, whatever the C shape on the calls (`do`/`while`, `for (;;)`, `goto`). Written as `while (!done)` on a flag set in the body, it is not rotated: that is the original `main` (100%, `notes/block08-diffs.md`). The same author's `custom_game` uses the same flag loop;
  - a coordinate derived from a loop index written in the expression (`i * 16 - sx`) rather than kept in a variable (`x`): VC6's own induction variable gets a stack slot after the user variables, which a variable never gets, and the test moves to it (`cmp eax, 0x150`) as in the original (`draw_level` 94.37% -> 100%, `notes/block03-diffs.md`);
  - one variable reused for two unrelated loops (the x of a first walk, then the y of a fall) decides the order in which VC6 reloads spilled variables after an inner loop: `bonus_room` 99.78% -> 100% (`notes/block05-diffs.md`); try renaming the variable of an earlier loop to each later local;
  - a call nested in an argument (`textout(..., 318 - text_length(...), 2, -1)`) makes VC6 push the arguments after it first and clean the stack of the previous calls; a local for the result (`len = text_length(...);`) lets the pops of several calls be grouped into one `add esp` (`draw_level`, `add esp, 0x40`);
- the shapes found in maped (2026-10-27, `notes/maped-diffs.md`):
  - separate `if`s rather than an `else if` chain when each branch ends the function anyway: the tails that VC6 merges between the branches differ (`draw_tile_mask` 90.53% -> 100%, `draw_tile_type`); VC6 also threads a jump to the end after `if (n == 28) m = 3;` (single known value) but not after `if (n == 124 || n == 87)` (`auto_mask`);
  - a `?:` between two constants that differ by one (`f79 & 8 ? 19 : 18`) gives `and` / `or 0x90` / `shr 3`, and so does the `if`/`else`, but only the `if`/`else` at its place among the other assignments gives the original registers (`FUN_004019b0`);
  - a value derived from an index written in the expression (`MIN(i + dx, w - 1)`) rather than kept in a second counter: VC6 creates the induction variable itself, with the original registers (`shift_map`);
  - a separate local for a value derived from another local (`x = DAT_0042a420 * 16 + mx`) rather than updating it in place (`mx = ... + mx`): the stack slots and registers of the whole 3,792-byte loop changed with it (`editor_loop` 45.46% -> 99.73%);
  - parameters reused as temporaries: `resize_map` only matches when its two parameters receive the new size, then the source tile (separate locals: 50.99%);
  - a file offset computed into a local before `fopen` rather than in the `fseek` call (`load_objects`);
  - `x + y` versus `y + x` decides which global is loaded first (`editor_loop`, F5);
  - `object_message` is inline in Allegro 4.0.3 (`allegro/inline/gui.inl`): `acquire_screen` / `proc(MSG_DRAW)` / `release_screen` / `D_REDRAWME` in a dialog procedure is that call (`FUN_004015d0`);
  - a loop over `int` bounds written `i <= 15` gives `jle`, `i < 16` gives `jl` (`select_help_text`, `pick_tile`).
  - a coordinate kept as a row counter and multiplied in the call (`row = -1; ... row++; ... row * 18`) rather than a coordinate variable (`y = -18; ... y += 18`): VC6 strength-reduces `row * 18` and puts its start value (-18) in the loop preheader, after the guard, as the original does; an assignment `y = -18`, wherever it is written, stays before the guard (`pick_tile` 97.83% -> 100%, 2026-10-28);
  - `m = MAX(m, old); t->t2 = m;` rather than `t->t2 = MAX(m, old);`: the maximum is computed in the mask's register and stored from it (`cmp ebx, ecx` / `jg` / `mov ebx, ecx` / `mov [t + 2], bl`); a variable zeroed at the top of the function (`old = 0;` next to `m = 0;`) is what puts `xor edx, edx` before the `imul` of the index (`auto_mask` 80.54% -> 96.86%, 2026-10-28);
  - VC6 merges identical instruction sequences at the start (and the end) of the two branches of an `if`/`else` **after** register allocation: when both branches give a pointer the same register, its computation moves above the `je` (and the stores share one tail); the original keeps them apart only because the registers differ (`auto_mask`);
  - a global loaded in a branch and again after a merge whose other paths go through a call is kept in a callee-saved register on the path without the call and reloaded right after the call (partial redundancy elimination): `set_screen_mode`, where the original reloads it after the merge; an unrelated store through a pointer between the two (a kill) gives the original registers, no natural shape found yet.
- the shapes found in loader (2026-10-27):
  - `num_bonus = num_normal = 0;` rather than two assignments: the stores keep the order of the assignments (`num_normal` first), but the order in which VC6 reloads the cached `num_bonus` and the import pointer of `pack_fgets` at the exit of the first loop follows the first variable written in the source; two assignments gave 99.44% in either order (`main` `0x00401000`);
  - `""` is emitted by cl 12 as a 1-byte COMDAT in `.bss` (all zero), so the linker places it at the start of `.bss`, before `errno` (loader `0x00406708`), away from the other strings of the function.
- **zero-extended load of a byte global** [verified 2026-10-27, test programs]: VC6 loads an `unsigned char` global compared with an `int` as `xor ecx, ecx` / `mov cl, [g]` when it only sees an `extern` or a tentative definition, but as `mov ecx, dword ptr [g]` / `and ecx, 0xff` when it knows the alignment: `static` or initialised definition in the same file, a member at a 4-aligned offset of a structure, or an element of an array. A scan of the whole game code (`0x00401000`-`0x0040AD4F`) finds the second form for two globals only: `DAT_0042f550` (`0x00402D43`, `0x00402D7E`, `0x00403B5D`, `0x004097A8`, in blocks 03, 05 and 07) and `DAT_0042f564` (`0x00402C21`), while `DAT_0042f568` uses the first form (`0x004096AF`...). **Decided with the user on 2026-10-27**: the globals at `0x0042F500`-`0x0042F567` are one structure, `PLAYER player` (`happy.h`); the old `DAT_0042f5XX` are now `player.x`, `player.y` and `player.fXX` (XX = offset in the structure, e.g. `DAT_0042f550` = `player.f50`). `take_item` went from 85.55% to 100% and no other score changed.

Scratch tools for this (not versioned): compile one file with the project flags and print the `/FAs` listing of one function; try every order of a group of statements against a target instruction sequence (8 compilations in parallel: the 5,040 orders of 7 statements take 3.5 minutes). Often several orders give the same code (`FUN_00403030`): the source order is then not observable, and the comment says so.

## 3b. Ghidra

Names and types are carried from `src/` into Ghidra after each batch with `scripts/ghidra_sync.py` (dry run by default; `--apply` writes, `--save` writes then saves). It reads the `FUNCTION`, `LIBRARY` and `GLOBAL` annotations (not `src/crt/`) and only calls `rename_function`, `rename_symbol`, `set_function_prototype` and `apply_data_type`, with `strict_mode=off` (the server's naming gate wants PascalCase and a `g_` prefix, which `src/` does not use). Allegro types that Ghidra lacks (`BITMAP`, `DATAFILE`...) become `void *` in prototypes; a global of such a type only gets its name. A `DAT_<address>` name of `src/` keeps Ghidra's default name (`DAT_...`, `OBJ_ARRAY_...`). Functions that Ghidra misses (`timer_1s`, `timer_15ms`) are skipped: creating them is not allowed.

Structures go first, by hand: `import_data_types` with the structure text of the header. Importing an existing name **replaces** the type in place, and the arrays already typed with it follow [verified 2026-10-27, `OBJ`].

Pitfalls [verified 2026-10-27]:
- **Auto-analysis queue**: every write (prototype, applied type) queues analysis tasks. A `save_program` sent while they run waits behind them, and the whole HTTP server blocks: every request times out (here for hours, until Ghidra was restarted after a manual save showed "30+ wait for analysis" tasks). `ghidra_sync.py --save` waits for `analysis_status` to report `analyzing: false` before saving. A write can also fail during the analysis ("Invalid signature" on a valid prototype) and succeed afterwards.
- **Do not use `modify_struct_field` / `add_struct_field`**: retyping a field shrank `OBJ` from 28 to 16 bytes (later fields packed down) and renamed it with a Hungarian prefix (`x` -> `nX`). Repaired by re-importing the structure.
- `rename_symbol` on an address without defined data creates a label.

Backup from before the first write: `happy-decomp_2026_10_27.gar`.

Consequence: `captures/ghidra-cache/*_rest.json` is the Ghidra project **before** the renames. Regenerating it (`ghidra_dump_rest.py`) and then `inventory.py` would change the `ghidra_name` column of `notes/data/functions-*.csv`. Keep the cache as is unless the inventory itself must be redone.

## 4. CRT names: `scripts/crt_names.py`

The local `LIBC.LIB` is the game's (`toolchain-vc6.md` §4). The script reads it directly (ar format, then COFF), and for each CRT or THUNK function of the inventory looks for a symbol of a code section whose bytes are identical. The bytes covered by a relocation of the .obj are ignored, as is the alignment padding at the end. The name is the COFF symbol, decorated as in the PDB (`_free`).
- Ambiguities (several names for the same code) are resolved through the relocations, in both directions: a REL32 of the .obj to symbol S must land on a function that can carry the name S.
- Asm bodies with internal labels (`_memcpy`, `_memmove`, `__global_unwind2`, `__local_unwind2`) are compared up to the end of the section: status `verified (spans labels)`.
- Several public names at the same offset of the same .obj are aliases (`__strcmpi` = `__stricmp`): the name Ghidra gives is kept.
- `COMPILER_ALIASES` replaces a name by the one that the recompiled game code calls, since reccmp names a call target after the recompiled PDB [verified 2026-10-27]: `__alloca_probe` -> `__chkstk` (both public at offset 0 of `chkstk.obj`; the CRT calls the first, cl the second for a frame over 4 KB, loader `main` `0x00401005`), `__chdir` -> `_chdir` (the OLDNAMES alias, §3), `__itoa` -> `_itoa` (OLDNAMES, happy `draw_level`).
- `jmp [IAT]` of 6 bytes: import thunks generated by the linker (`RtlUnwind`, and maped's 7 Allegro thunks), not annotated.
