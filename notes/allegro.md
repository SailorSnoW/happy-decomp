# Allegro: version of `alleg40.dll` and how the exes use it

Date: 2026-10-27. Inventory phase, no changes made to Ghidra.

Sources:
- `game/alleg40.dll` (read-only) and its unpacked copy `captures/alleg40_unpacked.dll` (`upx -d`, upx 5.2.1).
- `scripts/pe_allegro.py`: direct parsing of the PE headers, the Rich header, the DLL's export table and the import tables of the three exes.
- `notes/data/alleg40-exports.csv`: the 1,292 exports of the DLL (ordinal, address, name, section, code/data).
- `notes/data/alleg40-imports.csv`: the 154 `alleg40.dll` imports of the three exes (ordinal, resolved name, IAT slot, address in the DLL).
- Ghidra MCP: `list_imports` on the three exes, then `get_xrefs_to` and `get_disassembly` on a few call sites.
- Official Allegro 4.0.3 sources: `all403.zip` (2,818,254 bytes, SHA-256 `8BFF4998…AB7D8F9C`), downloaded from the GitHub release `liballeg/allegro5` tag `v4-0-3` (https://github.com/liballeg/allegro5/releases/download/v4-0-3/all403.zip; tag created 2003-04-18 21:01 UTC according to the GitHub API). Extracted into `captures/allegro-4.0.3/src/allegro/`. The page https://liballeg.org/old.html only lists 4.0.0; the other 4.0.x releases are in the GitHub releases `v4-0-x` and on SourceForge (`sourceforge.net/projects/alleg/files/allegro/4.0.3/`).

All are later than the DLL (2003-04-19), which is consistent. [hypothesis] The DLL's date matches the public release of 4.0.3 in spring 2003 (recollection, not verified here).

## 3. Exports of the DLL

- [verified] 1,292 exports, all named, **ordinal base 1**: 1,016 in `.text` (code) and 276 in `.data` (variables). Full list in `notes/data/alleg40-exports.csv`.
- [verified] No forwarded export (forwarder).
- [verified] The GUI procedures `d_*_proc` (ordinals 129–147) are exported as code. There are also `_gui_*_proc` exports (`_gui_shadow_box_proc` `0x10026890`, `_gui_ctext_proc`, `_gui_button_proc`, `_gui_edit_proc`, `_gui_list_proc`, `_gui_text_list_proc`).

### Block of "out-of-line" copies of the inline functions

- [verified] A contiguous block of exported code runs from `0x10026A10` (`bmp_read24`) to `0x10027F00` (`persp_project_f`). It is followed by `_grow_scratch_mem` (`0x10027F40`), then by `install_joystick` (`0x10027FA0`), which belongs to another module. The block contains exactly the functions that Allegro 4 declares inline in its headers: `fixmul`, `draw_sprite`, `getr16`, etc. (list in §5).
- [verified in the sources] This is `src/inline.c`: `#define AL_INLINE(type, name, args, code) type name args code` then `#include "allegro.h"`, "Copies of the inline functions in allegro.h, in case anyone needs to take the address of them". The block corresponds exactly to the `AL_INLINE`s of the headers (§5).
- [hypothesis] The out-of-line version is compiled by the DLL's compiler (build 8966). It may therefore differ slightly from the code inlined by 8168 in the game. It remains a good reading reference.

### Observations on the imports

- [verified] All 3 exes import `_WinMain`, `install_allegro`, `install_keyboard`, `install_mouse` and `set_gfx_mode`.
- [verified] No exe imports the common drawing functions `draw_sprite`, `putpixel`, `getpixel`, `rectfill`, `hline`, `vline`, `line`, nor `fixmul`, `fixdiv`, `itofix`, `fixtoi`, `fixsin`, `fixcos`. Yet the game draws and does fixed-point arithmetic (see §4.1). [strong hypothesis] These calls are inlined from the headers.
- [verified] `happy.exe` imports the variables `_cos_tbl` and `allegro_errno`. [hypothesis] These imports are the signature of the inline `fixsin`/`fixcos` and of the asm versions of `fixmul`/`fixdiv`. Confirmed in §4.1.
- [verified] `packfile_password("happy")`:
  - `happy.exe`: `push 0x004124B0` at `0x00401F24`, then `call [0x00411184]` (IAT slot of `packfile_password`) at `0x00401F29`. The file bytes at offset `0x124B0` are `happy\0`.
  - `maped.exe`: `push 0x0040F1B0` / `call [0x0040D160]` at `0x00401C2B`/`0x00401C30` and `0x004028B8`/`0x004028BD`. Offset `0xF1B0` contains `happy\0`. Two other references have no determined argument: `0x0040196A` (`mov edi,[packfile_password]`, later call through `EDI`) and `0x004024D8` (`call` placed right after a `push ebp` at `0x004024D7`, itself right after a `ret`).
- [verified] `maped.exe` contains linker-generated `jmp [IAT]` import thunks, from `0x00405CA0` to `0x00405CC2`, for `d_check_proc`, `d_radio_proc`, `d_edit_proc`, `d_text_proc`, `d_button_proc`, `d_ctext_proc` and `d_shadow_box_proc`. They are the only references to their IAT slots. [hypothesis] These thunk addresses serve as constant values in static `DIALOG` arrays. These thunks are produced by the linker and do not need to be decompiled. `d_slider_proc` is called directly (`call [0x0040D190]`, referenced at `0x00401674` and `0x0040168C`). [hypothesis] These calls come from a game dialog procedure that delegates to `d_slider_proc`.

Consequences:
- [verified] The game uses **the MSVC asm versions** of the fixed-point maths. The C versions (`fmaths.inl:55-142`, active only with `ALLEGRO_NO_ASM`) go through `double`s: `fixmul` = `ftofix(fixtof(x) * fixtof(y))`. They would produce FPU code, which is absent here.
- [strong hypothesis] The game was compiled with inlining enabled (`/Ob1` or higher, probably `/O2`), without `ALLEGRO_NO_ASM` or `ALLEGRO_USE_C`. Under MSVC, `AL_INLINE` expands to `__inline __declspec(dllimport) type __cdecl` (`almsvc.h:72`). No exe imports `fixmul` or `draw_sprite`: all uses were therefore inlined.
- [verified in the sources] `_set_errno_erange` is declared `INLINE` (= `__inline`), without `_AL_DLL` (`al386vc.h:101`). It is not exported by the DLL, which explains the local copy at `0x00402110`.
- [verified in the sources] `END_OF_INLINE(name)` creates a `_force_instantiate_name` variable only if `AL_INLINE` is defined before including the headers, i.e. only in `inline.c` (`almsvc.h:64-68`). The game therefore contains no such variables.
- [verified] The functions that contain these inline asm blocks keep an `EBP` frame (`push ebp ; mov ebp,esp` at `0x00401F00` and `0x00404C50`). The arguments of the inlined functions are copied into local variables (`[EBP-4]`, `[EBP-8]`, `[EBP-0x18]`).
- [hypothesis] `_set_errno_erange` has a single copy (`0x00402110`) for 10 callers spread over two functions. This is consistent with a COMDAT copy deduplicated by the linker.

- `ftofix` and `fixacos`/`fixasin` write to `*allegro_errno`. An import of `allegro_errno` therefore does not by itself prove that the asm is present. Here, it is the instruction sequence that proves it.
- `rectfill` contains `ASSERT(bmp)`. No assertion code appears at `0x00404BEE`, so the game was compiled without `DEBUGMODE` [strong hypothesis].
- Outside the block, these are real functions, not inline ones: `fixatan`, `fixatan2`, `fixsqrt`, `fixhypot`, `triangle`, `draw_gouraud_sprite`, `masked_blit`, `makecol`, `makecol8`. `fastline` does not exist in 4.0.3.

### 5.3 `static INLINE` compatibility functions (`alcompat.h`)

Active unless `ALLEGRO_NO_CLEAR_BITMAP_ALIAS` or `ALLEGRO_NO_FIX_ALIASES` is defined.

## 6. Use in the decompilation

- [verified] The official 4.0.3 headers, configured for MSVC, are in `3rdparty/allegro-4.0.3/` (provenance: its `README.md`); the import library is generated from `lib/msvc/allegro.def` by `LIB /DEF` (`scripts/build.py`) and imports **by ordinal**, like the exes (`notes/toolchain-vc6.md` §6).
- [verified] The inline functions of §5 compiled from these headers give the code of the exes: the functions that use them match at 100%, except `play_level`, whose one difference is in the game code after a `fixmul` (`notes/open-diffs.md`). The out-of-line copy `0x00402110` (`_set_errno_erange`) is annotated as library code.
- **Decided on 2026-10-27** (`CLAUDE.md`): the "no inline assembly" rule targets the game's code; the Allegro headers are included as is, asm included. In the C17 port, `fixmul`/`fixdiv` etc. will be rewritten with 64-bit integer arithmetic, to reproduce the asm's truncation (`imul`/`shrd`) exactly. [verified in the sources] The C versions of Allegro 4.0.3 go through `double`s and round to nearest: `fixmul` = `ftofix(fixtof(x) * fixtof(y))`, and `ftofix` adds ±0.5 (`fmaths.inl:33-46,105-108`), hence possible differences of 1 LSB.
