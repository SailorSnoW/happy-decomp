# Allegro: `alleg40.dll` and how the exes use it

The game links dynamically against Allegro 4.0.3 (`game/alleg40.dll`, UPX-packed, not decompiled). This note is what a reader of `src/` needs: which Allegro, what the exes import, and how the code that the Allegro headers inline into the game looks in the binary. Headers used for the build: `3rdparty/allegro-4.0.3/` (provenance in its `README.md`). The full `all403.zip` archive and the unpacked DLL (`upx -d`) can be kept locally in `captures/`, outside git.

## 1. Version: Allegro 4.0.3, MSVC DLL build

| Evidence | Status |
|---|---|
| Version resource of `alleg40.dll`: `FileVersion` = `ProductVersion` = `4.0.3`, `ProductName` `Allegro`, `Copyright © 1994-2003 Allegro Developers` | [verified] |
| Export `allegro_id` (ordinal 73) points at the string `"Allegro 4.0.3, MSVC"` (`0x10075010` in the unpacked DLL); `src/allegro.c:29` builds it from `ALLEGRO_VERSION_STR` and `ALLEGRO_PLATFORM_STR`, which is `"MSVC"` for the DLL build (`almsvc.h:31-35`) | [verified] |
| `lib/msvc/allegro.def` of 4.0.3: its 1,292 `name @ordinal` entries have exactly the DLL's ordinals | [verified] |
| `ALLEGRO_DATE 20030419` (`base.h`) is the day of the DLL's `TimeDateStamp` (2003-04-19 18:03 UTC) | [verified] |
| The exes import `text_mode` and `install_allegro`, and the DLL has no `_install_allegro_version_check`: 4.0 API | [verified] imports and exports; [hypothesis] that these mark the 4.0 branch |

[strong hypothesis] The game was compiled with the 4.0.3 headers: every by-ordinal import resolves to a name consistent with its call sites, and the inlined code (§5) is that of these headers; since 2026-10-28 every function using it matches at 100%.

## 2. The DLL

- [verified] PE32 i386, base `0x10000000`, linker 6.00, `TimeDateStamp` 2003-04-19. Its Rich header has a C compiler build **8966** (not the game's 8168) and `Linker600 8447 ×1` (the linker that also produced the import library the game was linked with, `notes/toolchain-vc6.md` §3). [hypothesis] It uses the dynamic CRT (`MSVCRT.dll` in its imports). None of this matters for matching: the DLL is not rebuilt.
- [verified] 1,292 named exports, ordinal base 1, 1,016 code and 276 data, no forwarders.
- [verified] The block `0x10026A10` (`bmp_read24`)–`0x10027F00` (`persp_project_f`) holds out-of-line copies of all the header inline functions: it is `src/inline.c` of Allegro ("Copies of the inline functions in allegro.h, in case anyone needs to take the address of them"). Compiled by 8966, they can differ slightly from the copies inlined by 8168 in the game, but they are a readable reference.

## 3. How `src/` uses Allegro

- `#include <allegro.h>` from `3rdparty/allegro-4.0.3/include`, configured for MSVC (`alplatf.h`: `#define ALLEGRO_MSVC`), **without** `ALLEGRO_NO_ASM` or `ALLEGRO_USE_C`: the MSVC asm of `al386vc.h` is what the game contains (§5.2). Including these headers as is, asm included, is the exception to the "no inline assembly" rule (`CLAUDE.md`, decided 2026-10-27).
- Import library `alleg40.lib`, generated by `LIB /DEF` from `lib/msvc/allegro.def` (`scripts/build.py`); it imports **by ordinal**, like the originals.
- Under MSVC, `AL_INLINE(type, name, args, code)` expands to `__inline __declspec(dllimport) type __cdecl name args code` (`almsvc.h:72`) and `INLINE` to `__inline` (`almsvc.h:74`). With `/O2`, every such call is inlined: no exe imports `draw_sprite`, `rectfill`, `fixmul`... [verified].
- [verified] No `DEBUGMODE`: the `ASSERT`s of the inline functions leave no code (e.g. `rectfill` at `0x00404BEE`).
- `LOCK_VARIABLE`, `LOCK_FUNCTION`, `END_OF_FUNCTION`... are empty under Windows (`internal/alconfig.h:170-177`) and leave no trace. `END_OF_INLINE` creates `_force_instantiate_*` variables only inside Allegro's `inline.c` (`almsvc.h:64-68`), not in the game.

## 4. Imports

[verified] All three exes import `alleg40.dll` **by ordinal only**, and otherwise only `KERNEL32.dll` (happy 45, maped 48, loader 41 entries). All three import `_WinMain`, `install_allegro`, `install_keyboard`, `install_mouse` and `set_gfx_mode`. Exported variables are imported too (`key`, `mouse_x`, `screen`, `gfx_driver`, `font`...); Ghidra types `key` as a function.

| Exe | `alleg40.dll` imports | Notable |
|---|---:|---|
| happy | 72 | input (keyboard, mouse, joystick, timers `install_int`/`rest`), graphics (`create_bitmap`, `blit`, `stretch_blit`, `stretch_sprite`, `rect`, `drawing_mode`, colour/translucency/light tables, `save_bitmap`), palette fades, text (`text_mode`, `textout*`, `textprintf*`), sound (`play_sample`, `play_midi`, `midi_pause`/`resume`, `set_volume`), datafiles (`packfile_password`, `load_datafile`), `file_select`, `alert`; variables `_cos_tbl` and `allegro_errno` (needed by the inline `fixsin`/`fixcos` and the asm `fixmul`/`fixdiv`) |
| maped | 64 | configuration (`set_config_file`, `get_config_int`, `get_config_string`), GUI (`do_dialog`, `popup_dialog`, `do_menu`, `alert`, `d_button_proc`, `d_check_proc`, `d_ctext_proc`, `d_edit_proc`, `d_radio_proc`, `d_shadow_box_proc`, `d_slider_proc`, `d_text_proc`), file names (`get_executable_name`, `replace_filename`, `replace_extension`, `exists`); no sound |
| loader | 18 | `_WinMain`, `install_allegro`, `install_keyboard`, `install_mouse`, `set_gfx_mode`, `makecol`, `allegro_message`, `gui_fg_color`, `gui_bg_color`, `file_select_ex`, `exists`, `get_executable_name`, `replace_filename`, `pack_fopen`, `pack_fclose`, `pack_fgets`, `pack_fwrite`, `pack_iputw` |

[verified] maped contains linker-generated `jmp [IAT]` thunks at `0x00405CA0`–`0x00405CC4` (6 bytes each) for `d_check_proc`, `d_radio_proc`, `d_edit_proc`, `d_text_proc`, `d_button_proc`, `d_ctext_proc`, `d_shadow_box_proc`: the addresses stored in its static `DIALOG` arrays. They are annotated `LIBRARY` in `src/maped/data.c` (§5.5). `d_slider_proc` is called directly through the IAT (from the slider callback, `src/maped/block_02.c`).

## 5. Header code in the exes, and how to recognise it

### 5.1 `AL_INLINE` C functions

Most are one call through the bitmap's vtable. [verified] `BITMAP.vtable` is at `+0x1C` (`gfx.h`), so the pattern is `mov reg,[bmp+0x1C]` then `call [reg+offset]` with the bitmap pushed first. `GFX_VTABLE` offsets (`gfx.h`, 4 bytes per entry):

| Offset | Entry | Inline function |
|---|---|---|
| `+0x00` | `color_depth` | `bitmap_color_depth`; `draw_sprite` tests the sprite's `== 8` |
| `+0x10` / `+0x14` | `acquire` / `release` | `acquire_bitmap`/`release_bitmap` (`acquire_screen`/`release_screen` on `screen`), called only if non-NULL |
| `+0x24` | `putpixel` | `putpixel` |
| `+0x34` | `line` | `line` |
| `+0x38` | `rectfill` | `rectfill` (e.g. `0x00404BEE`) |
| `+0x44` / `+0x40` | `draw_256_sprite` / `draw_sprite` | `draw_sprite` (8-bit sprite / other depths) |
| `+0x48`, `+0x4C`, `+0x50` | `draw_sprite_v_flip`, `_h_flip`, `_vh_flip` | same names |
| `+0x5C` | `draw_lit_sprite` | `draw_lit_sprite` |
| `+0x60` | `draw_rle_sprite` | `draw_rle_sprite` |
| `+0x6C` | `draw_lit_rle_sprite` | `draw_lit_rle_sprite` |
| `+0x9C` | `clear_to_color` | `clear_to_color` |

Used in `src/` (by the C, not counting comments): happy uses `rectfill`, `line`, `putpixel`, `draw_sprite` and its three flips, `draw_rle_sprite`, `clear_to_color`, `bitmap_color_depth`, `acquire_screen`/`release_screen` (in `blit_to_screen`, `src/common/block_01.c`); maped uses `rectfill`, `line`, `draw_sprite`, `draw_lit_sprite`, `draw_rle_sprite`, `draw_lit_rle_sprite`, `clear_to_color`, `object_message`. Real DLL functions despite similar names: `makecol`, `makecol8`, `masked_blit`, `stretch_sprite`, `fixsqrt`, `fixatan2`, `fixhypot`.

Fixed point (`inline/fmaths.inl:145-168`), used by happy only:
- `itofix(x)` = `x << 16`; `fixtoi(x)` = `fixfloor(x) + ((x & 0x8000) >> 15)`, i.e. `sar x,16` plus `sar`/`and 1` of the rounding bit (many sites in `0x00404C50`);
- `fixcos(x)` = `_cos_tbl[((x + 0x4000) >> 15) & 0x1FF]`, `fixsin(x)` = `_cos_tbl[((x - 0x400000 + 0x4000) >> 15) & 0x1FF]`: an indexed load from the imported `_cos_tbl` (e.g. `0x004034B0`–`0x004034FD` in `0x00403450`).

### 5.2 MSVC asm (`platform/al386vc.h`)

| Function | Lines | Pattern | In the game |
|---|---|---|---|
| `_set_errno_erange` | 101-106 | `*allegro_errno = ERANGE` (34); `INLINE` without `_AL_DLL`, not exported by the DLL | out-of-line copy `0x00402110` (§5.5) |
| `fixmul` | 157-178 | `imul`; `shrd eax,edx,16`; `sar edx,15`; overflow test, `call _set_errno_erange`, saturation to ±`0x7FFFFFFF` | 8 inlined copies in `play_level` (`0x00404C50`): four `fmul` calls (§5.3), each inside a `MIN`/`MAX`, which evaluates it twice |
| `fixdiv` | 187-220 | signs gathered in `ebx`, `shr edx,16`/`shl eax,16`, unsigned `div`, overflow → `call _set_errno_erange` | 2 sites in `init_game` (`0x00401F00`) |
| `fixfloor` | 230-237 | `mov eax,x ; sar eax,0x10` | through `fixtoi` |
| `fixadd`, `fixsub`, `fixceil`, `bmp_*_line`, `_default_ds` | 32-150, 246-261 | — | not used |

- These functions return their result in `eax` without `return` (`#pragma warning (disable: 4035)`).
- [verified] A function containing this asm keeps an `EBP` frame (`push ebp ; mov ebp,esp` at `0x00401F00` and `0x00404C50`), and the arguments of each inlined call are first copied to stack locals.
- The C versions (only with `ALLEGRO_NO_ASM`, `fmaths.inl:55-142`) go through `double`s and would produce FPU code, absent from the game; they also round where the asm truncates.

### 5.3 `alcompat.h` aliases

Unless `ALLEGRO_NO_FIX_ALIASES` is defined, `alcompat.h:41-71` defines the Allegro 3.x names as `static INLINE` wrappers: `fadd`, `fsub`, `fmul`, `fdiv`, `fceil`, `ffloor`, `fcos`, `fsin`, `ftan`, `facos`, `fasin`, `fatan`, `fatan2`, `fsqrt`, `fhypot` → `return fix*(...)`; likewise `clear(bmp)` → `clear_bitmap(bmp)` (lines 27-39). [verified by the match] They are not equivalent to calling `fix*` directly: `play_level` (`0x00404C50`) only matches with `fmul` in at least three of its four products, because the `return` changes the register allocation around the inlined asm (`src/happy/block_05.c`, `notes/matching.md` §3a).

### 5.4 Macros that leave a trace

- `END_OF_MAIN()` (`platform/alwin.h:44-48`): a `__stdcall` `WinMain(hInst, hPrev, Cmd, nShow)` that returns `_WinMain((void *)_mangled_main, ...)`. [verified] 12 instructions, `push <main>`, `call [_WinMain]`, `ret 0x10`, right after `main`: happy `0x0040A970` (`main` `0x0040A830`), maped `0x00405C70` (`0x00405AE0`), loader `0x004014A0` (`0x00401000`). reccmp finds it by symbol name (`// WinMain`).
- `allegro_init()` = `install_allegro(SYSTEM_AUTODETECT, &errno, atexit)` (`system.h:68`): three pushes, the CRT's `errno` and `atexit` (happy `0x00401F09`).
- `SCREEN_W`/`SCREEN_H` = `(gfx_driver ? gfx_driver->w : 0)` / `->h` (`gfx.h:249-250`): a NULL test of `gfx_driver`, then `+0x68` / `+0x6C` (happy `0x00404BB9`, maped `0x00401A44`).
- `MIN`, `MAX`, `MID(x,y,z)` = `MAX(x, MIN(y, z))`, `ABS` (`base.h:58-63`): used throughout `src/` for clamps; arguments are evaluated twice. [verified] VC6 may compile them branchless: `setle dl ; dec edx ; and edx,edi` at maped `0x00401B03`, in the clamps of `set_screen_mode` (`0x00401A20`).
- Constants folded at compile time: `KEY_*` (index into `key[]`), `GFX_*`, `DRAW_MODE_*`, `JOY_TYPE_*`, `DIGI_`/`MIDI_AUTODETECT`; timer macros such as `install_int(timer_1s, 1000)` (happy `0x00401F5D`).

### 5.5 Library code annotated `LIBRARY`

- happy `0x00402110` (4 instructions: `mov eax,[allegro_errno]`; `mov ecx,[eax]`; `mov dword [ecx],0x22`; `ret`): `_set_errno_erange`, emitted out of line because the asm of `fixmul`/`fixdiv` calls it; one copy for its 10 call sites. Annotated `// LIBRARY: HAPPY 0x00402110` in `src/happy/block_02.c`, not decompiled.
- maped `0x00405CA0`–`0x00405CC4`: the seven import thunks (§4), annotated in `src/maped/data.c` inside `#if 0`.
- The `WinMain` of `END_OF_MAIN()` is compiled from the macro and annotated as a normal `FUNCTION` (§5.4).
